# MySQL과 PostgreSQL 비교 — 채팅 프로젝트에서 알아둘 차이

작성일: 2026-11-07  
비교 기준: MySQL 8.4(InnoDB), PostgreSQL 18 공식 문서  
학습 배경: MySQL은 사용해 본 경험이 있고, 이번 채팅 프로젝트에서는 PostgreSQL도 경험해 보려 한다.

## 1. 이미 알고 있는 개념은 그대로 활용할 수 있다

두 DB 모두 회원, 채팅방, 참여자, 메시지를 테이블로 저장하고 관계를 연결할 수 있다. 기본적인 `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `JOIN` 개념도 공통이다.

기본키(PK), 외래키(FK), 고유값 제약(UNIQUE), 트랜잭션을 사용할 수 있다. PostgreSQL에서도 기존 MySQL 경험을 활용하면서 세부 문법과 설정 차이를 배우면 된다. [PostgreSQL 기능 소개](https://www.postgresql.org/about/), [MySQL InnoDB 소개](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html)

## 2. 처음 사용할 때 체감할 네 가지 차이

| 항목 | MySQL 8.4 | PostgreSQL 18 | 채팅 프로젝트에서 연결되는 부분 |
|---|---|---|---|
| 숫자 ID 자동 생성 | `AUTO_INCREMENT` | `GENERATED ... AS IDENTITY` | 회원·채팅방·메시지 ID 생성 |
| 중복 키가 있을 때 갱신 | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT ... DO UPDATE`; 무시하려면 `DO NOTHING` | 중복 이벤트 등의 처리 정책을 구현할 때 사용하는 문법 |
| 문자열 대소문자 비교 | 문자열의 collation에 따라 결정. 기본 `utf8mb4_0900_ai_ci`에서는 대소문자를 구분하지 않음 | 일반적인 `text`/`varchar`의 기본 비교에서는 대소문자를 구분. 구분하지 않는 비교도 별도로 구성 가능 | 로그인 ID·닉네임의 검색과 중복 판단 |
| JSON 저장 | 네이티브 `JSON` 타입과 관련 함수 제공 | `json`, `jsonb` 타입 제공. `jsonb`에 GIN 인덱스 등 사용 가능 | 나중에 메시지별 부가 정보를 저장할 때 검토 |

### ID 생성: 같은 목적, 다른 문법

아래는 문법 비교를 위한 작은 예시이며, 실제 회원 테이블 설계는 이후 별도로 진행한다.

```sql
-- MySQL
CREATE TABLE member_example (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    nickname VARCHAR(30) NOT NULL
);
```

```sql
-- PostgreSQL
CREATE TABLE member_example (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nickname VARCHAR(30) NOT NULL
);
```

두 예시 모두 `id`를 생략하고 새 행을 넣으면 DB가 값을 생성한다. PostgreSQL의 identity는 내부적으로 sequence를 사용하며, 자동 생성과 고유성 보장은 다른 역할이므로 예시처럼 `PRIMARY KEY`도 지정한다. [MySQL AUTO_INCREMENT](https://dev.mysql.com/doc/refman/8.4/en/example-auto-increment.html), [PostgreSQL Identity Columns](https://www.postgresql.org/docs/18/ddl-identity-columns.html)

### 중복 처리: INSERT에 붙이는 문법이 다르다

기본키나 고유값 제약과 충돌할 때 MySQL은 `ON DUPLICATE KEY UPDATE`, PostgreSQL은 `ON CONFLICT ... DO UPDATE` 같은 문법을 사용한다. PostgreSQL에서는 충돌 대상 열이나 제약을 지정할 수 있다. 두 문법의 세부 동작이 같지는 않으므로 SQL을 그대로 복사해서 옮기지는 않는다. [MySQL 중복 키 갱신](https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html), [PostgreSQL INSERT / ON CONFLICT](https://www.postgresql.org/docs/18/sql-insert.html)

회원가입에서 이메일이 중복되면 기존 회원을 덮어쓰는 것이 아니라 가입을 거절하는 정책을 먼저 구현한다. 중복 갱신 문법은 그 정책이 필요한 기능에서 사용한다.

### 문자열 비교: 회원가입에서 실제로 신경 쓸 차이

예를 들어 로그인 ID `Ming`과 `ming`을 같은 값으로 볼지 정해야 한다.

- MySQL에서 대소문자를 구분하지 않는 collation을 사용하면 같은 값으로 비교할 수 있다. MySQL이 항상 대소문자를 무시하는 것은 아니다.
- PostgreSQL의 일반적인 문자열 비교에서는 서로 다른 값이다. 대소문자를 무시하려면 비교 규칙을 별도로 구성해야 한다.
- 서비스에서 같은 ID로 취급하기로 했다면 입력 처리, 조회, DB의 중복 방지 제약이 같은 규칙을 따르도록 설계한다.

`collation`은 문자열의 비교·정렬 규칙이다. 이 설명은 문자열 **값**에 대한 것이며 테이블 이름의 대소문자 규칙과는 별개다. [MySQL 문자열 비교](https://dev.mysql.com/doc/refman/8.4/en/case-sensitivity.html), [PostgreSQL 대소문자 비교와 고유성](https://www.postgresql.org/docs/18/citext.html)

### JSON: 두 DB 모두 지원한다

MySQL의 `JSON`도 유효성 검사와 내부 바이너리 저장 형식을 지원한다. PostgreSQL의 `jsonb`는 JSON 데이터를 처리하기 위한 형식으로 저장하고 다양한 검색 연산과 인덱스를 제공한다. MySQL에도 JSON에서 값을 추출한 생성 열 등에 인덱스를 두는 방법이 있다. 지원 함수, 연산자, 인덱스 구성 방식이 다르다. [MySQL JSON](https://dev.mysql.com/doc/refman/8.4/en/json.html), [PostgreSQL JSON / JSONB](https://www.postgresql.org/docs/18/datatype-json.html)

이번 프로젝트의 첫 버전에서는 회원·채팅방·메시지를 일반적인 열과 테이블로 설계하고, JSON이 필요한 데이터가 생기면 적용을 검토한다.

## 3. Spring Boot에서 달라지는 부분

Spring Boot에서는 DB에 맞는 JDBC 드라이버와 접속 URL을 설정한다. 이후 JPA를 사용하더라도 직접 작성한 SQL이나 DB 전용 타입까지 모두 호환되는 것은 아니므로 사용하는 DB에서 동작을 확인한다. [Spring Boot SQL 데이터베이스 연결](https://docs.spring.io/spring-boot/reference/data/sql.html)

현재 `webmvc`와 `validation`은 HTTP API와 입력값 검증을 위한 의존성이다. DB 연결·저장을 위한 의존성과 설정은 다음 단계에서 추가한다. [기존 Gradle 의존성 정리](../spring-boot/gradle-dependencies.md)

## 4. 이번 프로젝트에서 선택하는 기준

MySQL은 익숙해서 기능 구현에 집중하기 좋고, PostgreSQL은 기존 SQL 지식을 바탕으로 다른 DB의 동작과 운영을 경험하기 좋다. 새로운 DB를 경험하려는 학습 목적에 맞춰, 이번 프로젝트에는 PostgreSQL을 추천한다.

이 채팅 서비스를 구현하는 데 두 DB 모두 사용할 수 있다. 이 문서는 성능 벤치마크가 아니며, 어느 쪽이 항상 빠르다고 판단하지 않는다. 나중에 성능을 비교한다면 실제 조회 패턴, 인덱스, 데이터 양, 서버 설정을 맞춰 측정한다.

다음 학습 단계는 **로컬 PostgreSQL 실행 → 프로젝트용 DB·접속 계정 생성 → Spring Boot 연결 → 회원 테이블 설계**다. 이 문서는 비교 자료이며 설치나 DB 생성 완료 기록은 아니다.
